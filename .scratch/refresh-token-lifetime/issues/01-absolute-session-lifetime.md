# 01: Bezwzględny limit życia sesji

**What to build:** Refresh token wydany przy jednym logowaniu przestaje działać po ustalonym czasie od tego
logowania, niezależnie od tego, jak często user go odświeża; potem user loguje się ponownie. Dziś każda
rotation przesuwa termin ważności o 7 dni od wymiany, więc sesja używana co tydzień nie wygasa nigdy.
Wylogowanie i unieważnianie tokenów są poza zakresem, do osobnej decyzji.

**Blocked by:** None (can start immediately)

**Status:** done

- [x] Wartość limitu ustalona przy triage: 30 dni od logowania.
- [x] Odświeżenie po przekroczeniu limitu daje ten sam błąd co nieważny refresh token.
- [x] Rotation działa jak dotąd w granicach limitu.
- [x] Test z kontrolowanym czasem pokrywa wygaśnięcie po limicie mimo regularnych odświeżeń.

Decyzja użytkownika w trakcie (po RP2): wiersze sprzed migracji mają `logged_in_on_utc = '-infinity'`, które
Npgsql czyta jako `DateTime.MinValue` z `Kind=Unspecified`. Przy samym cap pierwsze odświeżenie takiego wiersza
dawało 500: rotation liczyła `MinValue + 30 dni` (`Unspecified`), a Npgsql odmawia zapisu takiej daty do
`timestamp with time zone`. Wybrany wariant: warunek w handlerze refresh przed rotation,
`LoggedInOnUtc + 30 dni < now` → `UserErrors.InvalidRefreshToken`. Skutek przy wdrożeniu: każdy refresh token
sprzed migracji przestaje działać przy pierwszym odświeżeniu, więc wszyscy zalogowani userzy logują się
ponownie. Backfill (np. `expires_on_utc - 7 dni`) wymagałby ręcznej edycji wygenerowanej migracji, czego
konwencja zabrania. Opis tego wariantu w pytaniu o model („stary wiersz przejdzie jeszcze jedno odświeżenie”)
był błędny; wyszło to dopiero w red proof.
