# Add a Domain Entity

Create a new entity and wire it through every layer, following the `TodoItem` pattern.

## Files to create/modify

1. **Entity** — `src/Domain/{Feature}/{Entity}.cs`

```csharp
using SharedKernel;

namespace Domain.Projects;

public sealed class Project : Entity
{
    public Guid Id { get; set; }
    public Guid OwnerId { get; set; }
    public string Name { get; set; }
    public DateTime CreatedAt { get; set; }
}
```

`sealed class`, inherits `Entity` (gives it `DomainEvents` + `Raise(...)`), `Guid Id`, plain settable properties, collections initialized with `= [];`.

2. **Error catalog** — `src/Domain/{Feature}/{Entity}Errors.cs`

```csharp
using SharedKernel;

namespace Domain.Projects;

public static class ProjectErrors
{
    public static Error NotFound(Guid projectId) => Error.NotFound(
        "Projects.NotFound",
        $"The project with the Id = '{projectId}' was not found");
}
```

Codes are `"{FeaturePlural}.{Reason}"`. Pick the factory by semantics: `Error.NotFound` (404), `Error.Conflict` (409), `Error.Problem` (400), `Error.Forbidden` (403), `Error.Failure` (500).

3. **Domain events** — one record per file, `src/Domain/{Feature}/{Entity}{PastTenseVerb}DomainEvent.cs`

```csharp
using SharedKernel;

namespace Domain.Projects;

public sealed record ProjectCreatedDomainEvent(Guid ProjectId) : IDomainEvent;
```

Create at minimum the `Created` event; add others as commands need them. Events carry ids, not entities.

4. **EF configuration** — `src/Infrastructure/{Feature}/{Entity}Configuration.cs`

```csharp
using Domain.Projects;
using Domain.Users;
using Microsoft.EntityFrameworkCore;
using Microsoft.EntityFrameworkCore.Metadata.Builders;

namespace Infrastructure.Projects;

internal sealed class ProjectConfiguration : IEntityTypeConfiguration<Project>
{
    public void Configure(EntityTypeBuilder<Project> builder)
    {
        builder.HasKey(p => p.Id);

        builder.HasOne<User>().WithMany().HasForeignKey(p => p.OwnerId);
    }
}
```

Relationships are configured shadow-style (`HasOne<User>().WithMany()`) — entities hold foreign-key ids, not navigation properties. Configurations are picked up automatically by `ApplyConfigurationsFromAssembly`.

5. **DbContext wiring** — add `DbSet<{Entity}> {Plural}` to **both**:
   - `src/Application/Abstractions/Data/IApplicationDbContext.cs`
   - `src/Infrastructure/Database/ApplicationDbContext.cs`

   Also add the `DbSet` to `tests/Application.UnitTests/Abstractions/TestDbContext.cs` so handlers stay unit-testable.

6. **Migration** (run `dotnet tool restore` first on a fresh clone) — from the repo root:

```
dotnet ef migrations add Add_{Plural} --project src/Infrastructure --startup-project src/Web.Api
```

Migration names are `PascalCase_With_Underscores` (see `Add_RefreshTokens`).

## Rules

- The Domain project references only `SharedKernel` — no EF, no Application types. Persistence concerns (keys, conversions, relationships) live exclusively in the Infrastructure configuration.
- Run `dotnet tool restore` (once per clone), then `dotnet build CleanArchitecture.slnx` and `dotnet test CleanArchitecture.slnx` when done — `ArchitectureTests` enforce the layer rules.
- Red proof for mappings: integration tests replay migration files via `MigrateAsync`, so editing only the configuration class, without a migration, fails every integration test at startup with `PendingModelChangesWarning` — a crash, not a red proof. Check `dotnet ef migrations list --no-connect` shows the new migration. If a test depends on a mapping rule (a unique index, a cascade delete), remove that rule from the generated migration once and watch the test fail for that reason. Before breaking, record `sha256sum <file>` (PowerShell `Get-FileHash`). Restore by re-editing the exact original text — never `git checkout`, `git restore` or `git stash` (they discard the rest of the uncommitted work) — and confirm the hash matches. `git diff` alone proves nothing: it omits untracked new files. Leave no `.bak` copies.
- `dotnet ef` (10.x) writes `// <auto-generated />` and its `#pragma warning disable` lines into the `.Designer.cs` file only. Make `// <auto-generated />` the first line of the new migration file too (after the BOM), as in the earlier migrations; without it the analyzers fail the build (e.g. IDE0161). That header goes only on files `dotnet ef` generated. Otherwise leave migration files as generated; the only exception is the temporary red-proof edit above, restored byte-identical (BOM included — compare `sha256sum`).
- **Existing rows.** A non-nullable column added to a table that already has rows gets a default for them from
  the migration. For a `DateTime` on PostgreSQL that default is `'-infinity'`, which Npgsql reads back as
  `DateTime.MinValue` with `Kind=Unspecified`; date arithmetic on it stays `Unspecified`, and saving the result
  to `timestamp with time zone` throws (HTTP 500). EF InMemory unit tests never show it. Before the migration,
  settle with the user what an existing row means (for example a guard that treats it as expired; a backfill
  means hand-editing the generated migration, so it is the user's call), and give the old-row path a test with
  a `DateTime.MinValue` fixture.
- If the user also wants use cases for the entity, continue with the `add-feature` skill.
